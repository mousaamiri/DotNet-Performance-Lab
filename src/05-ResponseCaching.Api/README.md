# 05 - Response Caching (Output Caching)

<div dir="rtl">

## دربارهٔ این پروژه

این پروژه به بررسی عملی مکانیزم Output Caching در ASP.NET Core می‌پردازد و تفاوت آن را با Response Caching سنتی (مبتنی بر هدرهای HTTP) روشن می‌کند. برخلاف پروژه‌های قبلی که کش به‌صورت دستی در سطح کد پیاده‌سازی می‌شد، در اینجا کش‌سازی به‌طور کامل توسط میان‌افزار (Middleware) چارچوب مدیریت می‌شود و تنها با اعمال یک ویژگی (Attribute-like) روی endpoint فعال می‌گردد.

## پیش‌نیاز اجرا

از آنجا که در این پروژه Redis به‌عنوان محل ذخیره‌سازی Output Cache پیکربندی شده است (`AddStackExchangeRedisOutputCache`)، پیش از اجرای پروژه باید یک نمونهٔ در حال اجرای Redis (برای مثال از طریق Docker) در دسترس باشد؛ در غیر این صورت میان‌افزار کش با خطا مواجه خواهد شد.

## سناریو و پیاده‌سازی

مراحل انجام‌شده در این پروژه به شرح زیر است:

- **ثبت سرویس Output Cache**: فعال‌سازی Output Caching با `AddOutputCache` و پیکربندی Redis به‌عنوان Backing Store آن با `AddStackExchangeRedisOutputCache`، به‌جای ذخیره‌سازی پیش‌فرض در حافظه.
- **افزودن میان‌افزار**: استفاده از `app.UseOutputCache()` به‌جای `app.UseResponseCaching()`. این انتخاب آگاهانه بوده و به‌منظور تمایز عملی بین دو رویکرد در کامنت کد مستند شده است.
- **شبیه‌سازی منبع داده**: پیاده‌سازی `DataService` که سفارش‌ها را از یک فایل JSON محلی می‌خواند و با یک تأخیر عمدی (`Task.Delay(2000)`) در متد `GetOrderAsync`، واکشی یک آیتم منفرد را کند شبیه‌سازی می‌کند.
- **اعمال کش روی endpoint**: استفاده از `.CacheOutput(op => op.Expire(TimeSpan.FromSeconds(10)))` روی `GET /orders/{id}` جهت کش کردن پاسخ به مدت ۱۰ ثانیه، بدون نیاز به هیچ منطق دستی Cache-Aside در بدنهٔ handler.
- **اندازه‌گیری**: ثبت زمان پاسخ‌دهی واقعی سرویس داده (`QueryTime`) در بدنهٔ پاسخ و چاپ یک پیام (`Handler called!`) در کنسول، جهت تشخیص اینکه آیا handler اصلاً برای یک درخواست خاص فراخوانی شده یا پاسخ مستقیماً از کش بازگردانده شده است.
- **بررسی هدرهای HTTP دستی (غیرفعال)**: نگهداری کد مربوط به تنظیم دستی `CacheControl` (به‌صورت کامنت) جهت مقایسهٔ رویکرد مبتنی بر هدر (Response Caching) با رویکرد سمت سرور (Output Caching).

## مفاهیم کلیدی

- تفاوت **Output Caching** (مکانیزم جدید، سمت سرور، مستقل از هدرهای HTTP و قابل ذخیره در Backing Storeهای مختلف نظیر Redis) با **Response Caching** (مبتنی بر هدرهای استاندارد HTTP مانند `Cache-Control`، که می‌تواند توسط مرورگر یا CDN نیز تفسیر شود).
- امکان استفاده از Redis به‌عنوان Backing Store برای Output Cache، که آن را برای معماری‌های چندنمونه‌ای (Scale-Out) مناسب می‌سازد.
- عدم نیاز به نوشتن منطق دستی بررسی/ذخیرهٔ کش در سطح کد؛ کل فرآیند توسط میان‌افزار و پیکربندی اعلانی (`CacheOutput`) مدیریت می‌شود.
- اهمیت تفکیک بین زمان واقعی پردازش سرویس (`QueryTime`) و مشاهدهٔ فراخوانی یا عدم‌فراخوانی handler، به‌عنوان روشی برای اثبات Cache Hit/Miss بدون وابستگی به هدرهای پاسخ.
