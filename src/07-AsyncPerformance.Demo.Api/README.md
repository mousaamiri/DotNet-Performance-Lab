# 07 - Async Performance & Thread Pool Starvation

<div dir="rtl">

## دربارهٔ این پروژه

این پروژه به بررسی عملی و **اندازه‌گیری‌شده** یکی از خطرناک‌ترین آنتی‌پترن‌های رایج در ASP.NET Core می‌پردازد: **sync-over-async** (بلاک کردن روی کد async با `.Result` یا `.Wait()`). هدف این نیست که فقط ادعا شود این کار بد است، بلکه با یک ابزار Load Testing دست‌ساز (پروژه‌ی جداگانه‌ی `07-LoadTester.Console`)، تفاوت واقعی در عملکرد سرور زیر فشار همزمان اندازه‌گیری و مستند شده است. در کنار آن، تفاوت `Task<T>` و `ValueTask<T>` نیز در سناریوی داده‌ی کش‌شده بررسی می‌شود.

## سناریو و پیاده‌سازی

### سرویس API (`07-AsyncPerformance.Demo.Api`)

سه endpoint تعریف شده که همگی از یک منبع داده (فایل JSON محلی) می‌خوانند، اما با سه الگوی متفاوت:

- **`GET /orders/sync-over-async`**: عمداً از `.Result` روی `Task<List<Order>>` استفاده می‌کند — الگوی نادرست که Thread فراخوانی‌کننده را تا پایان عملیات async بلاک می‌کند.
- **`GET /orders/proper-async`**: همان عملیات را با `await` صحیح انجام می‌دهد؛ Thread حین انتظار برای I/O آزاد می‌شود.
- **`GET /orders/valuetask-demo`**: از یک متد `ValueTask<List<Order>>` استفاده می‌کند که نتیجه را در یک فیلد (`_cachedOrders`) کش می‌کند؛ در صورت وجود کش، بدون تخصیص (allocation) یک `Task` جدید مقدار را برمی‌گرداند.

نکتهٔ مهم پیاده‌سازی: `DataService` باید به‌صورت **Singleton** ثبت شود، نه Scoped — در غیر این صورت فیلد `_cachedOrders` بین درخواست‌های مختلف مشترک نخواهد بود و مسیر «کش‌شده» در `ValueTask` هرگز عملاً تست نمی‌شود.

### ابزار Load Testing ([`07-LoadTester.Console`](../07-LoadTester.Console))

به‌جای استفاده از ابزارهای آماده مانند `bombardier` یا `k6`، یک ابزار Load Test ساده و اختصاصی با C# نوشته شده است تا هم به ابزار خارجی وابستگی نباشد و هم منطق آن کاملاً قابل‌فهم و قابل‌توسعه باشد:

- تعداد مشخصی درخواست (`concurrency`) به‌صورت **همزمان** (بدون `await` تک‌تک) ساخته و در یک لیست `Task` جمع‌آوری می‌شوند.
- با `Task.WhenAll` همگی رها می‌شوند و با `Stopwatch` زمان کل تا تکمیل همهٔ درخواست‌ها اندازه‌گیری می‌شود.
- این فرآیند برای هر سه endpoint (`sync-over-async`, `proper-async`, `valuetask-demo`) با concurrency یکسان تکرار می‌شود تا مقایسه‌ای منصفانه به‌دست آید.

## نتایج اندازه‌گیری

اندازه‌گیری‌ها بلافاصله پس از **ری‌استارت API** (یعنی با Thread Pool سرد و کش خالی) انجام شده‌اند تا اثر Thread Pool Starvation به‌وضوح دیده شود:

### Concurrency = 50 (اولین اجرا پس از ری‌استارت)

| Endpoint | زمان |
|---|---|
| `sync-over-async` | ۲۱۰۷ ms |
| `proper-async` | ۶۳۳ ms |
| `valuetask-demo` | ۲۵۰۱ ms *(کش هنوز خالی بود؛ شامل تأخیر بارگذاری اولیه)* |

### Concurrency = 250 (اولین اجرا پس از ری‌استارت)

| Endpoint | زمان |
|---|---|
| `sync-over-async` | **۲۶۷۰۵ ms** |
| `proper-async` | ۱۸۰۷ ms |
| `valuetask-demo` | ۳۶۶۹ ms *(کش هنوز خالی بود)* |

در بالاترین فشار تست‌شده (۲۵۰ درخواست هم‌زمان)، نسخهٔ `sync-over-async` نسبت به `proper-async` حدود **۱۵ برابر کندتر** بود.

### رفتار در اجراهای بعدی (بدون ری‌استارت API)

اجرای مجدد ابزار تست (بدون ری‌استارت سرور) در هر دو سطح concurrency نشان داد که فاصلهٔ زمانی بین سه endpoint به‌طور محسوسی کاهش می‌یابد و گاهی `sync-over-async` حتی از `proper-async` هم سریع‌تر ظاهر می‌شود. این نتیجه گمراه‌کننده است اگر بدون توضیح باقی بماند، بنابراین علت آن به‌صراحت مستند شده:

1. **گرم شدن Thread Pool:** .NET ThreadPool به‌صورت پویا و تدریجی تعداد Threadهای آماده را افزایش می‌دهد. پس از اولین موج فشار سنگین، Threadهای بیشتری در دسترس می‌مانند و اثر بلاک‌شدن در `sync-over-async` کمتر محسوس می‌شود.
2. **کش شدن داده در `valuetask-demo`:** پس از اولین فراخوانی موفق، `_cachedOrders` پر می‌شود و فراخوانی‌های بعدی بدون I/O واقعی و فوری بازمی‌گردند — این سرعت بالا مربوط به کش شدن داده است، نه صرفاً ماهیت `ValueTask`.

به همین دلیل، تنها اعداد **بلافاصله پس از ری‌استارت API** به‌عنوان مبنای مقایسهٔ Thread Pool Starvation در نظر گرفته شده‌اند؛ اجراهای بعدی صرفاً برای نمایش تأثیر warm-up و کش مستند شده‌اند، نه به‌عنوان مقایسهٔ اصلی.

## مفاهیم کلیدی

- **Thread Pool Starvation**: وقتی تعداد زیادی Thread به‌صورت هم‌زمان با `.Result`/`.Wait()` بلاک شوند، Threadهای آزاد استخر تمام می‌شوند و درخواست‌های جدید تا آزاد شدن یک Thread معطل می‌مانند؛ این وضعیت با افزایش فشار (concurrency)، به‌شکل نمایی بدتر می‌شود.
- **چرا async درست مقیاس‌پذیرتر است**: در الگوی `await` صحیح، Thread حین انتظار برای I/O (خواندن فایل، فراخوانی شبکه و ...) به استخر بازگردانده می‌شود و می‌تواند به درخواست‌های دیگر سرویس دهد؛ یک Thread می‌تواند عملاً به صدها درخواست هم‌زمان کمک کند.
- **تفاوت واقعی `Task<T>` و `ValueTask<T>`**: `Task` همواره یک شیء روی heap است، حتی اگر نتیجه از قبل آماده باشد. `ValueTask` یک `struct` است و در صورتی‌که نتیجه synchronously در دسترس باشد (مثلاً از کش)، هیچ تخصیص حافظه‌ای رخ نمی‌دهد. این تفاوت تنها زمانی محسوس است که واقعاً مسیر «نتیجهٔ آماده» طی شود، نه هر بار.
- **اهمیت طول عمر سرویس (Lifetime)**: ثبت نادرست یک سرویس دارای وضعیت داخلی (مثل کش) به‌صورت `Scoped` به‌جای `Singleton` می‌تواند کل فرض تست را بی‌اثر کند، حتی اگر منطق کش‌سازی به‌خودی‌خود درست نوشته شده باشد.
- **اهمیت اندازه‌گیری تکرارپذیر**: یک نتیجهٔ منفرد کافی نیست؛ باید شرایط تست (ری‌استارت شدن یا نشدن سرویس، سرد یا گرم بودن Thread Pool و کش) به‌وضوح مستند شود تا نتیجه‌گیری قابل‌دفاع باشد.
